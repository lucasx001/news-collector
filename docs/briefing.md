# A 股早晚简报

## 当前行为

- 来源：`cls-telegraph`、`cls-depth`、`wallstreetcn-quick`、`gelonghui`、`thepaper`、`ithome`、`36kr-quick`。
- 每天北京时间 08:00 汇总前一天 20:00 至当天 08:00 的新闻；20:00 汇总当天 08:00 至 20:00 的新闻。周末相同。
- 08:00–09:00、20:00–21:00 是延迟执行和重试窗口，每个窗口成功后不再发送。实际送达时间在采集、筛选、分析完成之后。
- 其余时间继续采集入库并更新待推送队列，不筛选、不翻译、不做 AI 分析、不发送通知。
- 时间按系统首次发现计算（包括窗口开始时启动的采集），不是新闻原始发布时间；窗口开始后首次发现的新闻进入下一份简报。
- 来源 ID 相同且 URL 或归一化标题相同，视为同一新闻；同源标题改动但 URL 不变也不重复发送。不同来源 ID 的重复报道保留，不做语义合并。
- 当前简报只支持平台新闻。RSS、独立展示区、新增热点区和翻译已关闭。RSS 意外启用时会报错，防止悄悄漏掉内容。
- AI 分类和分析只使用简报快照，不回读当天全集。无匹配新闻则不发空报告。

## 状态与失败处理

本地状态：`output/briefing/state.json`。远程状态：同一 R2 bucket 下的 `state/briefing-v1.json`。

状态保存待处理新闻、来源内去重摘要、分类标签缓存、待发报告快照及每个接收方的成功回执；不保存渠道密钥。每轮启动先加载状态，Railway 重启后继续使用同一份记录。请保留这个对象，不要对 `state/` 设置自动过期。

首次启用会从昨日和当日 SQLite 导入当前窗口的历史新闻。此前旧推送流程没有逐条回执，无法追溯旧版本实际推送过哪些新闻；新规则的去重保证从新状态建立后开始。

失败时保留快照，只重试尚未成功的接收方；未完成的旧报告优先重试，新新闻继续排队，可能顺延至后续窗口。过滤失败或分析失败不会将新闻标记为已处理。明确被兴趣筛选排除的条目会记为已处理，避免每天重复分类。

R2 状态读写出错时停止，不把权限错误或网络错误当作空状态，也不回退到本地状态。状态使用条件写入和 15 分钟租约防止容器重叠执行；异常退出后租约自动到期。仍建议 Railway 只运行一个采集副本。

消息平台和 R2 不支持跨系统事务。如果平台实际收到消息但响应丢失，或进程恰在送达后、回执持久化前退出，重试仍可能重复；超长消息分批发送时，部分批次成功、后续批次失败也有这个限制。

## 配置与部署

- `config/config.yaml`：`briefing.enabled: true`，`schedule.enabled: true`，`schedule.preset: custom`。
- `config/timeline.yaml`：统一管理推送时间和重试窗口。
- `config/ai_interests.txt`：A 股新闻兴趣和筛选条件。
- `config/ai_briefing_prompt.txt`：简报分析提示词，区分事实、传导路径和待核实信息，不将快讯列表顺序当成热度。

Railway 继续使用 `docker/Dockerfile`，部署代码后保持 `RUN_MODE=cron`、`CRON_SCHEDULE=*/30 * * * *`，不要只在早晚启动采集。保留原有 `AI_API_KEY`、通知渠道和 `S3_*` 配置。确认没有用环境变量将 `SCHEDULE_PRESET` 覆盖成其他模板，挂载配置目录的部署也需要同步更新配置文件。

R2 需允许读取及写入 `state/`；新的简报 HTML 同时保存到 `html/briefings/YYYY-MM-DD_HH-MM.html`。容器本地报告位于 `output/html/briefings/`，最新报告入口仍为 `output/index.html`。

新闻源 ID 来自现有 NewsNow 接口；源出现在上游列表不保证每个部署环境都能访问。部署后检查各来源成功/失败日志。本次开发环境访问聚合 API 返回 HTTP 403，未用真实 AI、通知或 R2 凭据执行线上验证。

回退原流程：关闭 `briefing.enabled`，再按需要恢复旧的 schedule、RSS、展示配置；保留简报状态供将来恢复使用。

## 验证

运行 `python -m unittest discover -s tests -v`。测试使用临时目录、模拟 AI 和通知，覆盖跨午夜、静默、同源去重、跨来源保留、部分失败重试、历史数据导入、远程状态恢复及损坏/权限错误。
